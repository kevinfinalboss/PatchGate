What it does

You describe what an instance should have in a catalog (agents, apps, hardening, drift rules). Instances pick it up with a tag. Patchgate takes it from there, in every account of the organization, from one central hub.

Bootstrap from tags

A new instance tagged Patchgate:Managed=true gets its agents, apps and hardening in about three minutes, verified by checksum.

CIS hardening + drift

Three engines (native controls, Ansible, DSC) with per-rule evidence. Manual changes are corrected or reported, per category and inside a maintenance window.

App lifecycle

App sets per instance, pinned versions, install, upgrade and remove. Pruning only ever removes what Patchgate installed itself.

Gated changes

Profile and app set changes roll out ring by ring (dev, then prod), with email approval per approver group and automatic revert on failure.

Architecture

Hub and spoke across an AWS Organization. Workload accounts only forward events and expose one execution role; all decisions are made in the hub. The catalog, in-VM executors and hardening engines live in a cloud-agnostic core.

Management (us-east-1) Hub control plane (us-east-2) Spokes, deployed by StackSet Single-account mode: hub and spoke in one account

How it flows

Three flows cover the life of an instance. All of them are event-driven, retried and auditable: no user_data, no agents of our own.

Spoke

Instance launches, starts, or its tags change

The spoke forwards the EC2 running event, or a change to Patchgate:Managed / Profile / AppSets, to the hub bus.

Hub

Resolver builds the plan

Assumes Patchgate-Execution, reads the tags, places the instance in its ring and approver group, and composes the plan from DynamoDB. Invalid configuration is refused, never applied.

Hub

One run per instance

A DynamoDB lock serialises runs (launch and tag events arrive together). A plan whose digest is already applied ends here.

Instance

Executor applies the plan

SSM Run Command delivers the compressed plan. The executor installs agents (sha256 verified, fails closed), reconciles apps and runs the hardening engine, writing per-rule evidence.

Hub

Tagged and reported

Patchgate:BootstrapStatus and the plan digest are written back as tags; the result is emailed.

Why this design

  • Event-driven instead of user_data: every run is visible, retried and auditable (ADR 0004).
  • The VM never reads the catalog or calls a cloud API to decide what to do: the plan is self-contained.
  • Starting an instance re-checks it; nothing runs when the digest matches.
  • Values that reach a shell are validated first; executors are idempotent.
Spoke

State Manager runs the drift document

Every 30 minutes on every managed instance; the executor skips the run unless the profile's interval (30m–24h) is due.

Instance

Re-checks agents, apps and hardening

Each category is enforce (correct) or audit (report only). Outside the profile's maintenance window, everything only reports.

Instance

Never skips a window

The first check inside each window corrects even if the interval has not elapsed, so a short window is not missed.

Hub

Findings are emailed

An io.patchgate event reaches the hub with the mode, the trigger and the window state: remediated, non-compliant or failed.

You

Or reconcile now

patchgate-cli instance reconcile <id> runs the check immediately, ignoring interval and window, and prints the result.

Verified in the lab

  • Apps reinstalled while hardening was only reported (mixed modes).
  • Outside the window: 7-Zip removed and LLMNR re-enabled were reported, not touched.
  • reconcile corrected both immediately.
  • 6h interval: the first run inside the window corrected; the next was not due.
You

Change a profile or app set

patchgate-cli apply validates it and pins the current revision: instances keep it until a rollout releases the new one.

Hub

Plan by ring and approver group

Affected instances are grouped by ring (from their account) and approver group (account default or an allowed Patchgate:Approvers tag).

Hub

Ring 0 (dev)

The new revision is released to dev, instances re-plan through the bootstrap workflow, health is checked, then a soak period. On failure: revert and stop.

Approvers

Email approval per group

Signed, single-use, expiring links open a confirmation page; only its button decides. Each group approves its own instances.

Hub

Ring 1 (prod)

Approved groups get the revision; rejected groups stay on the previous one. When everyone took it, it becomes the revision for all.

Verified in the lab (dev and prod accounts)

  • A change reached dev, waited the soak, emailed the approver and reached prod only after the link was approved.
  • A broken change failed in dev: dev was reverted, the rollout stopped, prod was never touched.

Design notes (ADR 0010)

  • Releases are content revisions (sha256), so re-seeded built-in documents are tracked too.
  • Unregistered accounts are treated as the most protected ring.
  • Rules for rings, groups, releases and quorum are pure, tested functions in the core.
  • OS patching (Phase 4c-2) reuses the same engine with snapshots and rollback.

What only the real lab revealed

Unit tests passed for all of these. Running on real instances, in real accounts, is what found them.

Duplicate launch events

Creating a tagged instance emits both running and a tag-change event. Two installers ran at once and Windows failed with MSI 1618.

A per-instance DynamoDB lock serialises runs, plus a retry while Windows Installer is busy.

A byte order mark

The CloudWatch agent config written by PowerShell carried a BOM, and the agent refused it on the first Windows run.

Configs are written as UTF-8 without BOM; tests reject a BOM.

sshd reads the first value

A drop-in that sorts before Patchgate's (00-oops.conf) silently won over the remediation.

Remediation neutralises the directive in every other file first.

CIS vs. the cloud

A CIS rule disables the only local administrator on EC2, which would lock out access; the full MOF also exceeded WinRM's envelope size.

Documented exclusions for EC2 and a larger local WinRM envelope before DSC runs.

Evidence that never came

Ansible applied the benchmark (rc=0) but no rule was recorded: the JSON callback prefixes task names with the role name.

The parser handles role-prefixed names; evidence is checked in the lab, not assumed.

Python 3.13 vs. 3.12

The Lambda layer lock was generated locally on 3.13 and missed a dependency the 3.12 runtime needed.

The lock is generated and tested inside the official Lambda image.

Empty command output

SSM returns no output for a multi-step document unless the step is named, so reconcile printed nothing.

The CLI polls the command, then reads the output of the right step.

Mocks don't check trust

The first real rollout stopped at discovery: the spokes trusted only the older hub roles, and moto does not enforce trust policies.

The rollout role is trusted by every spoke; the failure path stopped and emailed as designed.

An error no Catch can catch

A workflow task replaced its own input; the next state failed with States.Runtime, which Step Functions never routes to a Catch, so no email went out.

A static test rejects the pattern, and an EventBridge rule reports any rollout that ends abruptly.

Principles

Cloud-agnostic core

core/ never imports a cloud SDK (enforced in CI). Providers implement a contract; AWS is the provider today.

Verifiable supply chain

Every download carries a sha256 and fails closed. Ansible collections, DSC modules and Python wheels are hash-pinned.

Least privilege

The hub may only assume the execution role inside the organization; Run Command only targets managed instances; Patchgate only writes Patchgate:* tags.

Configuration as data

Catalog documents are validated against JSON Schemas, versioned with history and rollback, and refused when invalid.

Idempotent in the VM

Running a plan twice gives the same result. Pruning only removes what Patchgate installed.
